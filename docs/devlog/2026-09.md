### 2026-09-20 — Single-device interface live-validation utility

- Added a deliberately small integration utility that accepts one device target,
  platform, existing `DeviceCredentials`, and existing `TransportConfig`.
- The utility reuses `connect_device`, caller-owned `DeviceSession` lifecycle, and
  `InterfaceService`, then prints a concise summary of normalized records.
- Added a deterministic test confirming delegation, output, cleanup, and that the
  device password is not printed.
- No transport, capability, vendor command, or parser behaviour changed. Inventory,
  Excel, concurrency, reporting, REST, and provisioning remain out of scope.

### 2026-09-20 — Interface status normalization corrections

- Corrected Huawei VRP normalization so PHY `down` remains administratively up
  and operationally down, while `*down` is both administratively and
  operationally down. The Protocol column no longer overrides physical state.
- Corrected Cisco IOS-XR administrative-down spelling normalization for
  `admin-down`, `admin down`, and `administratively down`.
- Added focused parser regressions; the full suite passes 54 tests.

### 2026-09-20 — Reusable multi-vendor interface capability

**Objective**
- Implement the first reusable observation capability for interface descriptions and status across all five supported platform identifiers.

**Relevant skills**
- `interface-collector`, `jumphost-connectivity`, `cisco-network-cli`, `huawei-network-cli`, and `ubiquiti-network-cli`.

**Implementation**
- Added a normalized immutable `InterfaceRecord` and transport-agnostic `InterfaceService` suitable for workflows and future API consumers.
- Added isolated Cisco IOS/IOS-XE, IOS-XR, Huawei VRP, and Ubiquiti EdgeSwitch command/parser adapters.
- Reused caller-owned `DeviceSession` objects and preserved the validated `CiscoIOSCLI` prompt/echo behavior.
- Added vendor paging setup and explicit rejection detection. Adapters execute only approved primary collection commands and do not guess alternatives after rejection.
- Kept unavailable EdgeSwitch administrative status empty and made empty output distinct from malformed non-empty output.
- Deliberately excluded inventory, Excel tracking, concurrency, REST, and provisioning.

**Validation / Tests**
- Added deterministic tests for each platform covering paging, approved commands, normal and empty output, descriptions containing spaces, status normalization, malformed output, rejected setup, and rejected collection commands.
- `PYTHONPATH=src pytest -q` passes 50 tests.
- `ruff check src tests`, `ruff format --check src tests`, `mypy src`, `python -m compileall -q src tests`, and `git diff --check` pass.

**Known issues / Limitations**
- New IOS-XR, Huawei, and EdgeSwitch adapters have deterministic mocked coverage but no live-device validation yet.
- Huawei brief-output enrichment and the supported EdgeSwitch description fallback are not invoked because primary output supplies the fields currently modeled; rejection never triggers an automatic alternate command.

**Next step**
- Add inventory-driven workflow orchestration and tracking/reporting as separate layers consuming this capability.

### 2026-09-20 — Reusable Cisco IOS/IOS-XE interactive CLI

**Objective**
- Provide prompt-aware, reusable command execution above the existing device transport.

**Prompt / Request**
- Detect IOS prompts dynamically, disable paging, clean command output, and enforce read timeouts.

**Relevant skills**
- `.agents/skills/cisco-network-cli/SKILL.md`

**Files changed**
- `src/orbitflow/vendors/cisco/ios.py`, `src/orbitflow/vendors/cisco/__init__.py`
- `tests/test_cisco_ios_cli.py`, `README.md`, `DEVLOG.md`

**Implementation**
- Added an IOS/IOS-XE-specific interactive CLI that consumes `DeviceSession` without changing transport.
- Prompt reads use channel timeouts and monotonic deadlines rather than fixed sleeps.
- Paging is disabled at initialization and command echo, ANSI control sequences, and the trailing prompt are removed from results.
- Live validation found that a stale prompt could complete a newly sent command before its response arrived; command reads now synchronize on the command echo before accepting the final prompt.

**Validation / Tests**
- Unit coverage includes `#` and `>` prompt detection, paging setup and command execution, timeout behavior, dynamic prompt changes, and output cleaning.
- Added regression coverage for a stale prompt arriving before the paging command echo.
- Windows live-device validation passed on Cisco ASR920 `NSW-STLEON-21CANB-BAS1` using IOS XE 17.06.07.
- The live test confirmed correct prompt detection, successful `terminal length 0`, complete `show version` output, removal of the command echo and trailing prompt, and clean session teardown.
- This live validation confirms the stale-prompt regression is fixed in the merged implementation.

**Known issues / Limitations**
- The implementation is intentionally limited to IOS/IOS-XE; IOS-XR requires a separate CLI implementation.

**Next step**
- Integrate the CLI with a separately scoped Cisco collection workflow.

### 2026-09-20 — Standardized permissive host-key defaults

**Objective**
- Standardize the validated Windows and Linux behavior while retaining configurable strict verification.

**Prompt / Request**
- Default bastion and target-device verification to permissive handling, remove Teleport-specific known-host loading, and do not implement custom Teleport CA verification.

**Relevant skills**
- `.agents/skills/jumphost-connectivity/SKILL.md`

**Files changed**
- `src/orbitflow/transport/models.py`, `src/orbitflow/transport/linux.py`
- `tests/test_transport.py`, `README.md`, `DEVLOG.md`

**Implementation**
- Both `verify_bastion_host_key` and `verify_device_host_key` now default to `False`, using Paramiko's permissive `AutoAddPolicy` without persisting learned keys.
- Removed the attempted `~/.tsh/known_hosts` loading; no custom Teleport CA verification is implemented.
- Configurable strict mode remains available and loads normal system host keys with `RejectPolicy`.
- The Windows local-forward architecture and Linux `tsh proxy ssh` plus `direct-tcpip` architecture are unchanged.

**Validation / Tests**
- Windows and Linux live validation succeeded using permissive host-key handling.
- Added mocked coverage for permissive defaults and the retained Linux strict bastion mode.

**Known issues / Limitations**
- Permissive verification does not protect against machine-in-the-middle attacks.

**Next step**
- Provision trusted system host keys and enable strict verification where operationally practical.

### 2026-09-20 — Initial Python transport layer

**Objective**
- Provide one common device connection API over the validated Windows and Linux Teleport paths.

**Prompt / Request**
- Implement transport only, with mocked tests, safe cleanup, and no login/OTP automation.

**Relevant skills**
- `.agents/skills/jumphost-connectivity/SKILL.md`

**Files changed**
- `src/orbitflow/transport/*`, `src/orbitflow/__init__.py`, `tests/test_transport.py`
- `requirements.txt`, `README.md`, `.gitignore`, `DEVLOG.md`

**Implementation**
- Added `connect_device`, OS-specific Windows and Linux backends, typed settings, an owned session, and transport exceptions.
- Windows uses a temporary `tsh ssh -N -L` process; Linux uses `tsh proxy ssh`, Teleport key plus certificate, and `direct-tcpip`.
- Rejects unknown SSH host keys and closes resources on success and failure paths.
- Uses the target address, rather than the loopback forward address, for Windows SSH host-key lookup.
- Classifies Linux identity, proxy, and bastion failures as Teleport errors without exposing underlying authentication details.

**Validation / Tests**
- `PYTHONPATH=src pytest -q` passes 6 mock-only tests for both OS paths.
- `ruff check src tests`, `ruff format --check src tests`, `python -m compileall -q src`, and `git diff --check` pass.

**Known issues / Limitations**
- No live-device validation was performed at this initial implementation stage.
- Linux callers must discover and supply key/certificate paths from their active `tsh` profile.

**Next step**
- Integrate an approved credential provider and active-profile path discovery in a separately scoped task.


### 2026-09-20 — Device capability and future OSS architecture

**Objective**
- Define OrbitFlow's long-term architecture so reusable network-equipment functions can support both internal automation workflows and future external REST/OSS consumers.

**Prompt / Request**
- Separate reusable device operations from higher-level features, normalize device state into structured outputs, support deterministic analysis/remediation/troubleshooting workflows, and ensure the same capabilities can later be exposed through REST APIs as an OSS layer.

**Files changed**
- `AGENTS.md`
- `CURRENT_STATE.md`
- `docs/architecture/device-capability-oss-model.md`
- `docs/devlog/2026-09.md`

**Architecture / Decisions**
- OrbitFlow will evolve around reusable device capabilities rather than one-off workflow scripts.
- Vendor-specific commands and parsers remain isolated behind common capability-oriented interfaces.
- Higher-level features compose normalized device capabilities for audit, troubleshooting, provisioning, remediation, service assurance, and other operational tasks.
- Observation, analysis, planning, configuration application, verification, and recording remain separable.
- Future REST APIs, GUIs, schedulers, and OSS/BSS integrations must call the same internal application/capability interfaces instead of duplicating device logic.
- Normalized structured models should be reusable by workflows, reports, JSON/API responses, and future integrations.
- Raw vendor CLI should not become the primary external OSS abstraction.

**Validation / Tests**
- Documentation/architecture change only; no runtime behaviour changed.

**Known issues / Limitations**
- Exact Python interfaces, model classes, API framework, and endpoint schemas are intentionally deferred until capabilities are implemented incrementally.

**Next step**
- Use the interface-description collector as the first implementation that follows the reusable capability -> normalized model -> workflow/reporting pattern.
